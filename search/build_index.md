# Phase 4 — Azure AI Search: unstructured knowledge index

Grounds the agent in the **narrative** side of the story — the authoring standard, the escalation
policy, prior Monthly Progress Reports, and scope/spec docs — so a generated MPR reads like the last
one and follows house style. Structured facts come from the semantic model / Data Agent; **prose
grounding comes from here.**

## Corpus
Generated by `data_gen/docs_gen.py` into `docs/`, catalogued in `docs/corpus_index.json`:

| doc_type | example | why the agent needs it |
|---|---|---|
| `standard` | MPR Authoring Standard | house style, required MPR sections |
| `standard` | Schedule-Risk Classification & Escalation Policy | Red/Amber/Green thresholds + who to notify |
| `spec` | Change-Notice Template | format for the draft-change-notice action |
| `spec` | Project Falcon Scope Summary | project context for grounding |
| `prior_report` | Project Falcon MPR 2026-05 / 2026-06 | few-shot exemplars of a real MPR |

## Index: `project-knowledge`

| Field | Type | Attributes | Source |
|---|---|---|---|
| `id` | Edm.String | key | slug of `path` |
| `title` | Edm.String | searchable, retrievable | `corpus_index.title` |
| `doc_type` | Edm.String | filterable, facetable, retrievable | `corpus_index.doc_type` |
| `project_id` | Edm.String | filterable, retrievable | `corpus_index.project_id` (nullable) |
| `path` | Edm.String | retrievable | `corpus_index.path` |
| `content` | Edm.String | searchable, retrievable | full markdown body |
| `content_vector` | Collection(Edm.Single) | searchable (HNSW) *(optional)* | embedding of `content` |

- **Semantic configuration** `project-knowledge-semantic`: title field = `title`, content field =
  `content` — enables semantic ranking for grounding queries.
- **Vector (optional):** add `content_vector` (1536/3072 dims) via
  `AZURE_OPENAI_EMBED_DEPLOYMENT` for hybrid search. Skip for a pure keyword demo.
- **Typical agent query:** filter `doc_type eq 'prior_report' and project_id eq 'PRJ-001'` to fetch
  the last MPR as an exemplar; filter `doc_type eq 'standard'` for the escalation thresholds.

## Where the corpus lives (OneLake)
The Lakehouse is the **canonical home** for the corpus. `scripts/32_upload_docs_to_lakehouse.ps1`
publishes `docs/` + `corpus_index.json` to **`Files/knowledge/`** in OneLake (ADLS Gen2 DFS API), so the
docs are visible in Fabric alongside the data. `build_index.py` then reads them from OneLake and
**pushes** them into Azure AI Search.

> **Why push instead of the OneLake indexer?** Azure AI Search *does* have a native
> [OneLake files indexer](https://learn.microsoft.com/azure/search/search-how-to-index-onelake-files)
> that can crawl a lakehouse's `Files/` on a schedule with incremental change detection — Markdown is a
> supported format, so it would work for this corpus. We deliberately use **push** here because for a
> 6-doc demo it's simpler: no Search **managed identity** + **Contributor/Admin on the Fabric workspace**
> to configure, and it keeps the `doc_type` / `project_id` facets sourced from `corpus_index.json`
> (the indexer would need custom file metadata or a skillset to reproduce those). For a production
> "drop a file in the Lakehouse and it auto-indexes" story, prefer the OneLake indexer.

## Build it
```powershell
./.venv/Scripts/Activate.ps1
pip install azure-search-documents azure-identity python-dotenv

# 1. publish the corpus to the Lakehouse Files/ section (sets DOCS_SOURCE=onelake in .env)
pwsh -File ./scripts/32_upload_docs_to_lakehouse.ps1

# 2. (re)create the index and upload — reads from OneLake by default
python ./search/build_index.py
```
`build_index.py` reads `AI_SEARCH_ENDPOINT` / `AI_SEARCH_INDEX` from `.env`, authenticates with
`DefaultAzureCredential` (or `AI_SEARCH_ADMIN_KEY` if set), (re)creates the index, and uploads every
doc listed in `corpus_index.json` with its full body as `content`.

**Corpus source** is controlled by `DOCS_SOURCE` in `.env`:
- `onelake` (default when `FABRIC_WORKSPACE_ID` + `FABRIC_LAKEHOUSE_ID` are set) — read from
  `Files/<DOCS_ONELAKE_PREFIX>/` in the Lakehouse. OneLake reads use `DefaultAzureCredential`
  (workspace membership required).
- `local` — read straight from the repo `docs/` folder (offline / no Lakehouse).

## Acceptance
- Index reports 6 documents.
- Query `content` for "escalation" filtered to `doc_type eq 'standard'` returns the schedule-risk
